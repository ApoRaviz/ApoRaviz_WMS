# Compact internal IDs, stable public identities

User requests a robust, efficient implementation after discussing BIGINT versus UUID primary keys. This is an architectural storage change to the existing PostgreSQL 18 application, not a new business feature. The user authorizes implementation; preserve the runnable checkout and real data.

## Decision

Users, Projects, Clients and Warehouses receive `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. Existing textual IDs move unchanged to `public_id text NOT NULL UNIQUE`. Every relational foreign key to these entities becomes bigint. Repositories resolve public IDs at their boundary and join on numeric keys; API `id`, URLs, saved project selections, sessions and JSON audit snapshots retain their existing string identities. No JavaScript Number conversion of internal IDs is permitted.

New public IDs are generated by PostgreSQL 18 `uuidv7()::text`. Keeping text here is intentional: existing public identities include `apo`, `legacy-*` and UUIDs and cannot be cast to UUID without breaking links. This unique public lookup index remains a storage cost; numeric foreign keys remove repeated long identities from membership/session/settings/warehouse/audit relations. Business codes remain separate and unchanged.

Roles and permissions retain meaningful text keys. Session token hashes remain hashes. Audit already uses bigint identity. No generic entity framework, redundant IDs on relationship tables, new dependency, Client/Warehouse editing UI, or Inbound work is added.

Alternatives considered: native UUIDv7 PK reduces random insert locality cost but retains 16-byte joins and requires legacy ID remapping; BIGINT exposed in API is compact but would break existing URLs/contracts. Numeric internal PK plus stable public ID is selected for compatibility with compact relationship keys.

## Migration and operations

Add migration 003; do not rewrite applied migrations. In one transaction, lock affected tables, create numeric parent identities, populate replacement FK columns through exact old-ID joins, assert required references via NOT NULL and validated FKs, replace keys/indexes, and preserve public IDs/business fields/audit JSON/password hashes/session tokens. Unexpected dependencies must fail and roll back, never CASCADE away external objects. Preserve original delete actions.

Create indexes matching real access paths: memberships(project_id,user_id), sessions(user_id), project_warehouses(warehouse_id), projects(client_id), and actor/update-user references, retaining composite PK/default/history indexes. Do not duplicate indexes already covered by leading PK columns.

Deployment requires a maintenance stop of old backend processes: old and new binaries are not schema-compatible. Use lock timeout to fail rather than wait indefinitely. Back up and verify restoration before real deployment; rollback after a committed migration requires matching database backup and previous binary. Do not reset public DB or auto-restart the user's servers in this task. Fresh install, populated upgrade, rollback-on-failure and repeated initialization are tested in isolated schemas.

## Verification

- Legacy fixture includes shared warehouses, members, session, nullable updated_by, settings and JSON audit. Numeric PK/FK types and original public joins/data must match after upgrade; rerun is inert.
- Foreign-key violations still fail; unknown public member IDs must not silently disappear through INSERT SELECT joins.
- IDs beyond JavaScript MAX_SAFE_INTEGER remain precise and private; new public IDs are UUIDv7 and numeric allocation remains database-owned under concurrency.
- Existing authentication, role scope, password/session revocation, audited settings, stale saves and all browser flows pass unchanged at the API boundary.
- Reproducible isolated measurement compares key/relationship index bytes for text UUIDv4, native UUIDv7 and bigint; report actual results and scope, not universal speed claims. Query plans check numeric indexed join paths at representative cardinality.
